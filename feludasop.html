Understanding a Feluda finding

Every finding follows the same basic structure.

Builder
● Need Your Check

Hero heading exceeds recommended character limit

Suggested fix: Shorten the hero heading to fit within a single line at standard viewport width.

Suggested fix location: Homepage → Hero section → Heading component.

Feluda expands the issue description in plain language when the caption and suggested fix are not enough on their own.
Issue captionImmediate understanding of what needs attention.
Suggested fixWhat should change to resolve it.
Fix locationWhere the change should be made.
Issue descriptionWhy Feluda flagged the issue.
4

Confidence labels

Every finding carries one of two labels — switch tabs to compare.

Builder
Important: Confidence is not the final decision. Both labels still require builder review and validation.
● Real Issue High confidence

Feluda believes this is a genuine issue.

Builder action:

  • Fix the issue on the website.
  • Review the implementation.
  • Select the checkbox to mark it accepted and fixed.
Agree? Fix it and mark it accepted / fixed.
Disagree? Use Keep as Is with a detailed justification.
● Need Your Check Human validation

Possible issue — needs human validation.

Common reasons Feluda asks for a check:

  • The website may have a valid exception.
  • The client may have specifically requested this implementation.
  • The finding may not apply to this website.
  • Feluda may have misread the implementation.
  • It may genuinely need correcting.
If it's real Fix it, then select Yes, Real.
If it's not real Select Not an Issue and explain why.
5

Feluda action options

What each builder response actually means.

Builder
✓

Yes, Real

For Need Your Check findings you agree with. Fix the issue — your confirmation also increases Feluda's confidence in that checkpoint.

×

Not an Issue

For Need Your Check findings that are incorrect or don't apply. Requires a clear, specific explanation — never a generic comment.

≋

Keep as Is

For either label, when you intentionally retain the current implementation for a valid business, client, design or process reason.

Example — mimic website: If Feluda flags a heading for exceeding the standard character limit but the content must follow the source site, select Keep as Is and explain the mimic-site exception.

Builder feedback — best practices

The single biggest lever for improving Feluda.

Builder

✕ Weak feedback

“Not an issue. Verified with TL.”
Low value for reviewers and checkpoint improvement

✓ Better feedback

“This is a mimic website, so the content intentionally follows the source website. Although the character count exceeds the standard limit, changing it would make the implementation inconsistent with the source. This type of finding should be excluded for mimic websites.”
Specific, factual, detailed and actionable
Avoid generic comments like “Not an issue,” “Verified with TL,” “Checked with mentor,” or “This is intentional.”

Builder do's, don'ts & key principles

The habits that make Feluda work well for everyone.

Builder
Review every findingDon't ignore findings because they're marked Need Your Check.
Validate against real requirementsWebsite, client requirements and exceptions matter.
Fix genuine issuesUse Yes, Real for confirmed Need Your Check findings.
Explain valid exceptionsKeep as Is always needs a meaningful reason.
Use KT and learningReduce repeated quality issues over time.
Improve through feedbackDetailed feedback makes Feluda more accurate for everyone.
Key principle: Feluda is an assistant, not a replacement for judgment.
